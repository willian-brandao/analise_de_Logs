Timestamps acuradas são um dos componetes mais críticos de uma análise de logs efetiva. As correlações baseadas em tepo, são a principal estrutura da detecção, investigação, e reconstrução dos incidentes de segurança. Quandos marcas de tempo estão desalinhads através de diferentes sistemas, analistas podem interpretar de forma errada a sequência de eventos ou ignorar indicadores chave.

Assegurar que todos os sistemas usam um tempo consistente e sincronizado é uma prática fundamental nas operações de ciberseguraça. Isso é cumprido usando o Protocolo de Tempo de Rede ou (NTP), que permite que dispositivos atualizem regularmente seus relógios interno de uma origem confiável.

## Entendendo os Timestamps

A maioria dos logins contém timestamps que indicam quando um evento ocorre. Porém, o formato, timezone, e a precisão desses timestamps podem variar significamente depedendo da origem.

### Formatos comuns do timestamp:

1. Tempo local legível para humanos
```
Jun 30 14:22:43
2025-06-30 18:45:12
```

2. Hora UTC com deslocamento de fuso horário
```
2025-06-30T18:45:12+00:00
2025-06-30T18:45:12Z
```
3. Tempo Epoch/Unix (valor inteiro em segundos desde 1970-01-01)
```
Timestamp: 1751372712 → Human time: 2025-06-30 18:45:12 UTC

```
4. Registro de data e hora de alta precisão com milissegundos ou microssegundos
```
2025-06-30T18:45:12.783Z
2025-06-30 14:22:43.154 +0200

```

Cada um desses formatos pode ser usado em diferentes ambientes ou ferramentas, como syslog, logs de servidor web, logs de nuvem, ou plataformas de SIEM.

## Discrepâncias em Timezones na Análise de Logs 

Timezones desalinhadas é um problema comum durante invesgação de incidentes. Por exemplo, se um log de firewall em UTC, um log de servidor Linux em um fuso horário (UTC-3), e a aplicação de logs do servidor está no fuso horário UTC+1, logo o mesmo evento vai aparecer em três tempos diferentes. 

Isso leva a:

* Interpretação errada da ordem de um evento.
* Gaps na lógica da correlação.
* Incidentes incorretos na timeline.
* Falsos positivos nas regras de detecção.

 ### Cenário de exemplo

 Três logs de diferentes dispositivos, mostrando o mesmo evento:

 **Servidor Linux (UTC-3):**
```
Jun 30 15:12:02 sshd[2991]: Accepted password for joao from 10.0.0.10

```

**Firewall (UTC)**
```
2025-06-30T18:12:02Z src=10.0.0.10 dst=192.168.1.20 action=accept

```

 **Log de Aplicação(UTC+1)**

```
2025-06-30 19:12:02 user=joao login_success=true
```

## NTP

NTP é um protocolo que sincroniza os relógios dos sistemas com servidores de tempo designados. Quando implementado corretamente, ele assegura que todos os sitemas dentro da infraestrutura mantenham o tempo consistentemente, geralmente sincronizado com o Tempo Universal Coordenado (UTC).

### Configuração Linux**

Para habilitar e verificar a sincronização NTP:

``
sudo timedatectl set-ntp true
timedatectl status
``

Saída:

```
Local time: Mon 2025-06-30 15:00:00 -03
Universal time: Mon 2025-06-30 18:00:00 UTC
NTP synchronized: yes

```

### Configuração do Windows

Configuração do NTP são controlados via painel de controle ou Powershell

```
w32tm /query /status
w32tm /resync
```

**Boas Práticas:**

* Usar um servidor NTP interno ou um pool de servidores NTP públicos.
* Evitar confiar em relógios de sistemas de BIOS ou hardwares.
* Monitorar e alertar em sitemas que se desviam dos tempos com  acurácia.
* Mormalizar timestamps para UTC nas plataformas de SIEM para assegurar uma correlação consistente.

## Normalização de Timestamps em Pipelines de Logs

Muitas organizações normalizam timestamps no estágio de ingestão de logs. Por exemplo, Logstash ou FLuent Bit podem analisar e converter vários formatos de timestamps em um campo padronizado como @timestamp em UTC. 

**Exemplo Logstash:**

```
filter {
  date {
    match => [ "log_time", "yyyy-MM-dd HH:mm:ss" ]
    target => "@timestamp"
    timezone => "UTC"
  }
}
```

Sistemas SIEM como Splunk ou Elastic Search dependem fortemente da análise de timestamps para alertas, correlação e visualizações de linha do tempo. Timestamps analisados ​​incorretamente ou ausentes frequentemente fazem com que os eventos sejam indexados fora de ordem ou excluídos da lógica de detecção.
