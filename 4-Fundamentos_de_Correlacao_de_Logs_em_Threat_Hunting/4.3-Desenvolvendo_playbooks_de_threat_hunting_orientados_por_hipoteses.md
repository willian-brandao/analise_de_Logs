## Introdução

Diferente das triagens de alerta reativo, threat hunting é proativo e orientado por inteligência. Isso requer hipótese de formulação sobre comportamento de ataques potenciais e validar algumas hipóteses através de análise de logs de correlação. 

Um playbook de hunting é um processo repetido e documentado que:

* Começa de uma hipótese bem estruturada.
* Define um escopo e requer logs de origem.
* Apresenta procedimentos passo a passo.
* Usar consulta específicas e lógica de correlação.
* Finaliza com documentação e feedback para engenharia de detecção.

Essa abordagem ajuda o Blue Team evita busca aleatórias em log e, em vez disso, a se concentrarem em descobrir padrões de comportamento do adversário que frequentemente burlam as detecções baseadas em assinaturas. 

---

## O que é uma Hipótese de Threat Hunting?

Uma hipótese é uma declaração que assume um comportamento de ataque específico ou técnica que pode ter ocorrido em seu ambiente.

Exemplo de Hipóteses:

* "Um adversário tem persistência estabelecida usando tarefas agendadas."
* "Há um comportamento de sinalização (beaconing) ocorrendo via HTTP a cada 60 segundos."
* "Um usuário interno acessando dados sensíveis que eles geralmente não toca."

Boas hipóteses são específicas, testadas e alinhadas ao adversários.

## Construindo o Playbook Etapa por Etapa

### 1. Definir a Hipótese

  Adversários podem ter persistência alcançada usando *schtasks.exe* em endpoints com logins de VPN recentes.

### 2. Configurar objetivos

   * Identificar máquinas onde tarefas agendadas criadas manualmente.
   * Juntar ações para atividade de usuários.
   * Detectar execução de tais tarefas.
   * Identificar qualquer payloads ou conexões de saídas associadas a eles.

### 3. Identificar Origem de Logs
   
|            Origem           |    Dados Necessários                                           |
|-----------------------------|----------------------------------------------------------------|
|  Logs de Eventos do Windows |   Criação de Tarefa ( Id de Evento 4698, execução de processo  |
| Logs de EDR                 | Corrente de processos pai/filho (schtasks.exe)                 |
| Logs de VPNs                | Timestamp de Acesso Remoto e usuários                          |
|   Logs de Proxy/DNS         | Qualquer  tráfego de saída pós-execução de tarefa              |

### 4. Criar Consultas de Pesquisas 

Splunk

```
index=windows EventCode='4698 CommandLine="*schtasks*"
| stats count by host, user, CommandLine, _time
```

Elastic KQL 
```
event.action: "sheduled-task-created" AND process.name : "schtasks.exe"
```
 Pivotagem para VPN

```
index=vpn user=$user$ earliest=-15m latest=+15m
```

### 5. Definir Timeline e Regras de Correlação 

* Login VPN de um IP Remoto.
* Dentro de 15 minutos: criação de tarefa agendada.
* Dentro de 5 minutos: execução um binário desconhecido.

### 6. Documentar e Automação

* Capturar árvore de processos, tarefas e linhas de comando.
* Adicionar reportes de hunting e detecção de backlog.
* Criar uma nova regra de Sigma se o comportamento é confirmado.

## Exemplo Prático: Hipótese para Exfiltração de Dados

Hipótese: Um host comprometido está exfiltrando dados via powershell codificado por meio do HTTP.

Plano: 

1. Pesquisar por logs de proxy por POSTs frequentes ou grandes de domínios desconhecidos.
2. Identificar user-agents com Powershell(ex: microsoft.powershell/5.1).
3. Pivotar logs de EDR para confirmar o uso de *Invoke-WebRequest* ou *Invoke-Expression*.
4. Combinar com tarefas agendadas ou persistência WMI no mesmo host.

## Formato Visual do Playbook de Hunting 

```
 # Playbook Name: Beaconing via DNS
- **Hypothesis**: Adversaries may be using DNS to exfiltrate data or beacon to C2
- **ATT&CK Techniques**: T1048.003 (Exfiltration Over Alternative Protocol), T1071.004 (Application Layer Protocol: DNS)
- **Logs Required**: DNS, EDR, Firewall, Proxy
- **Queries**:
    - DNS requests with high frequency to single domain
    - Unusual domain length (e.g. > 50 characters)
    - PowerShell processes making outbound connections
- **Expected Output**: List of endpoints with potential beaconing activity
- **Follow-up Actions**: Isolate host, extract memory, block domain
```
