## Introdução 

Sistemas Linux produzem uma larga variedade de logs que são essenciais para analisar de atividade de usuários, tentativas de autenticação, escalonamento de privilégio e comportamento de sistemas. Profissionais de Blue Team necessitam entender quando os logs são armazenados, como são estruturados, e como são interpretados para detectar comportamentos suspeitos como ataques de força bruta, acesso não autorizado ou uso indevido privilegiado. 

## Arquivos-chave em Sistemas Linux

| Arquivo de Log | Descrição |
|----------------|-----------|
| /var/log/auth.log | Autenticação, sudo, tentativa de login SSH |
| /var/log/secure   | Equivalente ao log de autenticação em distros baseados em RHEL |
| /var/log/syslog   | Eventos gerais de sistemas, mensagens de kernel |
| /var/log/messages | Daemon e mensagens de sistemas (RHEL/CentOS)    |
| /var/log/wtmp     | Registro binário de logins e reinicializações de usuários   |
| /var/log/btmp     | Tentativas falhas de login (binário) |
| /var/log/lastlog  | O último login de todos os usuários  |
| /var/log/sudo.log | Arquivos de logs sudo opcional ( depende da configuração) |

## Logs de Autenticação: SSH e Atividade Sudo 

Eventos de autenticação estão entre os logs mais críticos para o monitoramento da equipe de segurança. Eles ajudam a detectar ataques de força bruta, uso indevido de credenciais e movimento lateral.

**Exemplo: Falha de login SSH**
```
Jun 30 14:45:21 server sshd[1183]: Failed password for root from 192.168.0.10 port 54022 ssh2
```
Campos:
* Timestamp: Jun 30 14:45:21
* Processo: sshd[1183]
* Mensagem: Failed password
* Usuário: root
* IP de Origem: 192.168.0.10
* Porta: 54022
* Procotolo: ssh2

Caso de uso: Detecção de ataque de força bruta ou ataque de dicionário de um IP de origem específico.

**Example: SSH Successful Login**
```
Jun 30 14:45:24 server sshd[1183]: Accepted password for root from 192.168.0.10 port 54022 ssh2

```

Uma sequência de falhas seguidas por logins bem sucedidos de um mesmo IP de origem pode indicar que as credenciais foram adquiridas por meio de advinhação ou roubadas. 

## Detecção de uso do Sudo

Sudo permite que usuários executem comandos como outro usuário(tipicamente root). Monitorar o uso do sudo para detectar escalonamento de privilégio ou uso indevido. 

**Exemplo: Entrada de log de sudo (auth log):**
```
Jun 30 14:47:11 server sudo:     joao : TTY=pts/0 ; PWD=/home/joao ; USER=root ; COMMAND=/bin/bash

```
**Interpretação:**
* Usuário joao executando */bin/bash* como root.
* Executado do terminal *pts/0*, diretório atual */home/joao*

 Caso de uso: Identificar escalonamento de privilégio, movimento lateral, ou acesso ao shell como root. 

 **Configuração alternativa:**
 Alguns sistemas registram a atividade do sudo em um arquivo dedicado */var/log/sudo.log*, caso esteja habilitado:
 ```
Defaults logfile="/var/log/sudo.log"

```
## Comandos úteis no Linux para Análise de Autenticação 

1. Consulta de logins SSH
```
grep "Accepted password" /var/log/auth.log
```
2. Encontrar tentativas de logins falhos
```
grep "Failed password" /var/log/auth.log

```
3. Resumir por IP
```
grep "Failed password" /var/log/auth.log | awk '{print$(NF-3)}' | sort | uniq -c | sort -nr
```
4. Revisar o uso do sudo
```
grep "sudo" /var/log/auth.log
```
5. Mostrar logins recentes( do wtmp binário)
```
last
```
6. Mostrar falhas de logins (btmp binário)
```
lastb
```

## Detectar Casos de Uso de Anomalia

| Padrão | Indicador |
|--------|-----------|
| Múltiplas falhas de logins  | Tentativa de força bruta |
| Login em um tempo não usual | Ameaça interna ou conta comprometida |
| Uso de sudo por um usuário não autorizado | Escalonamento privilegiado | 
| Acesso SSH de um país/IP não usual | Possível movimento lateral |
| Mudança frequente entre usuários | Sequestro de sessão ou enumeração |

## Integração com SIEM 

Quando logs são encaminhados para SIEM, pode-se definir regras de detecção baseados em análise de campos como:
* event.source: sshd.
* event.outcome: success ou failure.
* user.name: root, joao, etc.
* source.ip: endereço IP de conexão.

### Exemplo de consulta SIEM (ELK/ElasticSearch):
```
{
  "query": {
    "bool": {
      "must": [
        { "match": { "event.module": "ssh" } },
        { "match": { "event.outcome": "failure" } },
        { "range": { "@timestamp": { "gte": "now-1h" } } }
      ]
    }
  }
}

```
A consulta detecta tentativas falhas de login SSH dentro da última hora. 

### Logins SSH baseado em chave (chaves não autorizadas)
```
Jun 30 15:12:33 server sshd[1542]: Accepted publickey for analyst from 10.0.1.5 port 49201 ssh2: RSA SHA256:abc123...

```
Caso de uso: Identificar quais usuários estão usando autenticação baseado em chaves. Pode ser usado por persistência por atacantes se as chaves foram adicionadas ao arquivo  *~/.ssh/authorized_keys*.

### Encerramento de Sessão
```
Jun 30 15:45:10 server sshd[1542]: Received disconnect from 10.0.1.5 port 49201:11: disconnected by user

```
Caso de uso: Detectar a duração da sessão e correlacionar o tempo de ínicio/fim da sessão para identificar das sessões de longa duração.

### Enumeração de usuários inválido 

```
Jun 30 16:03:22 server sshd[1638]: Invalid user testadmin from 203.0.113.5 port 53444
```
Caso de uso: Enumeração de usuários não existentes é o precursor de ataque de força bruta ou reconhecimento.

## Técnicas de Eventos Correlacionados

A forte capacidade de detecção envolve a correlação de múltiplos eventos correlacionados. Algumas técnicas de correlação incluem:

**1. Detecção de Força Bruta**
   - Padrão: Alto número de entradas de *failed password* dentro de um espaço curto de tempo.
   - Correlação: Único IP - múltiplos usuários ou múltiplas tentativas atribuídas a um único nome de usuário.
   - Resposta: Bloquear IP ou iniciar uma regra de bloqueio de conta.

**2. Inserção de Credenciais**
   - Padrão: Mesma tentativa de inserir senhas através de vários nomes de usuários.
   - Origem: Frequentemente, são obtidas por meio de ferramentas automatizadas que utilizam credenciais vazadas.

**3.Login bem sucedido depois de múltiplas falhas**
   - Padrão: *Failed password* x N -> *Accepted password*
   - Exemplo: 
     ```
      Jun 30 20:11:03 sshd[2311]: Failed password for root from 203.0.113.9  
      Jun 30 20:11:06 sshd[2312]: Failed password for root from 203.0.113.9  
      Jun 30 20:11:09 sshd[2313]: Accepted password for root from 203.0.113.9  
     ```
  Caso de Uso: Flag como comprometida se o login foi bem sucedido depois de múltiplas falhas.
  
**4.Atividade Usuário Não Usual**
 - Padrão: usuários que não possuem privlégio de usar o sudo para binários como *netcat*, *bash*, *wget*.
 - Detecção via:
   ```
    grep "sudo" /var/log/auth.log  | grep  -E 'nc|bash|wget|curl'
   ``` 
## Técnicas de Threat Hunting nos logs do Linux

**Técnica 1: Caçar Acesso de Root Interativo**

Procurar por sessões de shell diretas como root (especialmente as inesperadas):
```
grep 'COMMAND=/bin/bash' /var/log/auth.log | grep 'USER=root'
```
**Técnica 2: Procurar por movimento lateral via SSH**

Correlacionar eventos de login originados de IPs internos que não pertencem ao jump host (ou bastion host).
```
grep "Accepted password" /var/log/auth.log | grep -vE '192\.168\.0\.1|10\.0\.0\.1'
```
*Jump host / Bastion host: É um servidor intermediário usado como ponto único e controlado para acessar sistemas críticos (servidores, bancos de dados, dispositivos de rede).*

**Técnica 3: Monitorar picos repentinos de uso do comando sudo**

Gera uso frequente por usuário:
```
grep "sudo" /var/log/auth.log | awk '{print $1, $2, $3, $9}' | sort | uniq -c | sort -nr
```
É útil para marcar uso repentino ou não usual de contas que normalmente não fazem escalonamento.

**Técnica 4: Detectar Escanamento de enumeração de usuários**
```
grep "Invalid user" /var/log/auth.log | awk '{print $(NF)}' | sort | uniq -c | sort -nr
```
Rastrear nomes de usuário que estão sendo sondados para identificar tentativas de descoberta antes do acesso.

## Análise Sintática e Enriquecimento com Ferramentas

Uso do *ausearch* para auditoria
```
 ausearch -m USER_LOGIN -ts recent
 ausearch -ua 1001 
```

Útil para reaver sessões de logins especificas do usuários e mapear UID para nomes de usuários.

#### Exemplo de agregação de log com syslog para um servidor central
Configuration in /etc/rsyslog.conf
```
*.* @@logserver.local:514
```

#### Encaminhamento com auditd (audit.rules)
```
-w /etc/passwd -p wa -k passwd_changes

-w /bin/su -p x -k su_usage
```

Pode ajudar a rastrear uso de comandos e modificações críticas de arquivos.

## Exemplo de HoneyPot SSH e Comportamento de Logs

Exemplo de Honeypot Cowrie (imitando um serviço SSH)

```
2025-06-30T17:00:15 login attempt [admin:123456] from 103.123.98.12
2025-06-30T17:00:16 failed login attempt [admin:123456]
2025-06-30T17:00:17 failed login attempt [admin:qwerty]
```
Atacantes frequentemente usam credenciais comuns. Um pico em tentativas de logins de diversos IPs com nomes de usuários comuns indica um escaneamento automatizado.

| Indicador | Descrição |
|-----------|-----------|
| Múltiplas tentativas falhas de login | Ataque de força bruta ou preenchimento de credenciais |
| Uso de usuários inválidos | Enumeração ou escaneamento |
| Sucesso depois de múltiplas tentativas | Possível comprometimento de credenciais |
| Uso de chave SSH de fontes desconhecidas | Persistência via chaves autorizadas |
| Acesso SSH via IP não reconhecido | Potencial acesso externo não autorizado |
| Comando sudo suspeito | Tentativa de escalonamento privilegiado ou execução de download|


* Objetivo do Cowrie: Fazer o atacante acreditar que comprometeu um servidor Linux via SSH, enquanto você observa tudo sem risco real.*
