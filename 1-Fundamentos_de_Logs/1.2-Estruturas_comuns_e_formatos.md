# Estrutura e Formatos de Logs

## Introdução

Análise efetiva de logs não requer somente o entendimento quais são logs, e também como eles são estruturados. Logs vêm em vários formatos dependendo da sua origem, como sistemas operacionais, dispositivos de redes, ferramentas de segurança e servidores web. Um analista de blue team deve ser capaz de identificar o formato do log, analisar seus campos chave, e extrair informações relevantes para triagem, detecção e investigação.

Logs podem ser estruturados, semi-estruturados, ou sem estrutura. O formato usado afeta quão facilmente esses logs podem ser ingeridos por plataformas de SIEM, análise de ferramentas ou correlação através dos sistemas.

## Categorias de Formato de Logs

1. Logs em formato de texto

    Comuns em sistemas Linux e aplicações legadas. Eles são legíveis por humanos e orientado por linhas mas frequentemente requerem expressões regulares ou ferramentas como **grep** para análise.

2. Pares de Logs Chave-Valor

    Cada linha contém espaços separados por pares de chave-valor. Essa estrutura permite análise básicas e filtros.

3. Logs CSV

    Valores separados por vírgulas, úteis para exportação e análise em Excel ou ingestão por SIEMs.

4. Logs JSON

    Logs estruturados usados por aplicações modernas e ferramentas como Suricata, AWS CloudTrail, ou Elastic Beats. Facilmente analisadas por máquinas e pipelines de registro.

5. Logs XML

   Atualmente são menos comuns mas ainda é usado em sistemas legados e algumas empresas de software.

6. Logs Binários

   Exemplos incluem Logs de eventos do Windows (EVTX), que exigem ferramentas especiais como Event Viewer ou LogParser para realizar.

## Exemplos Práticos por Formato

1. Texto - Logs de auntenticação Linux

```
Jun 30 10:12:43 server sshd[1290]: Accepted password for admin from 192.168.0.12 port 50222 ssh2
```
Elementos chaves: timestamp, hostname, processos(sshd), messagens de status.
Caso de uso: Autenticação com sucesso, IP de origem, identidade de usuário.

2. Formato Chave-Valor - Log de Registro Diário

```
MESSAGE=Failed password for invalid user test from 10.1.1.5 port 50022 ssh2
PRIORITY=3
SYSLOG_IDENTIFIER=sshd
```
Caso de uso: Útil em sistemas baseados em Red-Hat usando journalctl. Fácil para extrair campos específicos. 

3. Formato CSV - Exportação de log de firewall

```
timestamp,src_ip,dest_ip,port,action
2025-06-30 12:01:55,10.0.0.5,192.168.10.1,443,allow
```
Caso de uso: Fácil de importar dentro de um SIEM ou planilhas para análises de comportamento de firewall.

4. Formato JSON - Alerta Suricata
```
{
  "timestamp": "2025-06-30T12:04:11.482Z",
  "event_type": "alert",
  "src_ip": "10.10.10.10",
  "dest_ip": "192.168.100.5",
  "alert": {
    "signature": "ET SCAN Nmap Scripting Engine",
    "severity": 2
  }
}
```
Caso de uso: O formato estruturado faz com que seja ideal para análises em SIEMs ou logs de pipelines como ELK. Permite campos de de queries como **alert.signature** ou **src_ip**.

5. Formato XML - Logs de Web Application Firewall

```
<event>
  <date>2025-06-30</date>
  <src_ip>172.16.0.8</src_ip>
  <event_type>SQL Injection Attempt</event_type>
</event>
```

Caso de uso: Algumas ferramentas mais antigas ou corporativas geram arquivos XML. É necessário usar XPath ou métodos similares para a extração.

6. EVTX (Binary)  - Logs do Windows Event

Podem ser vistos usando:
* A GUI Event Viewer.
* GET-WinEvent ou wevtutil via Powershell.
* LogParser ou ingestão por meio de um agente de SIEM.

Exemplo (Security.evtx, Event ID 4688):

```
A new process has been created.
New Process Name: C:\Windows\System32\cmd.exe
Creator Process: C:\Windows\explorer.exe
```

Caso de uso: Detectar processo suspeito executado no cmd, powershell ou rundll32.

## Padronização e Normalização de Campos

Desde cada origem de log tem seu próprio esquema, um dos grandes desafios em centralizar a análise de log é a normalização. Esse é o processo de conversão de diferentes formatos de logs e campos em um esquema comum. 

Por exemplo:

| Campos Brutos | Campos normalizados |
|---------------|---------------------|
| src_ip, src_address, ip.src | source_ip |
| username, user, acct | user_name        |
| timestamp, @timestamp, time | event_time |

Essa padronização é crítica em uma plataforma de SIEM como Splunk, Elastic Security ou QRadar para construir regras de detecção que trabalham através de múltiplas origens de dados. 

Considerações Práticas para Blue Team

* Utilize ferramentas de análise sintática e enriquecimento como Logstash, Fluent Bit, ou syslog-ng para converter e enriquecer dados de log.
* Construir dashboards baseadas em campos normalizados para para visibilidade multiplataforma.
* Validar que a origem dos logs produz saídas estruturadas sempre que possivel para facilitar a correlação e pesquisar.
* Entender como seu SIEM ingeri e analisa cada tipo de log.
